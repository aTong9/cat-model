# Liberty Cat Studio 设计哲学

> 适用范围：当前参数化 3D 猫生成器的 Web 编辑器、9901 Token 图鉴、2D/3D 对照、角色配置、场景预览与导出流程。

## 1. 产品体验主张

Liberty Cat Studio 不是传统的“后台表单”，也不是只供观看的 3D 展示页。它是一座可探索、可验证、可带走成果的数字角色工作室。

设计必须同时维护四种感受：

1. **角色始终是主角**：中央 3D 舞台占据视觉中心，工具退居边缘。
2. **创作是即时的**：用户修改参数后，应立刻看到角色发生变化。
3. **结果是可信的**：原始 NFT、当前 Trait、冲突规则和导出状态都可以追溯。
4. **复杂度是渐进的**：新用户可以随机生成和浏览，专业用户可以深入体型、配方、身份与导出。

一句话原则：**让用户先爱上角色，再理解参数，最后掌控系统。**

## 2. UE：User Experience，用户体验哲学

### 2.1 核心体验闭环

```text
发现一只猫 → 看懂它的来源 → 调整一个特征 → 即时确认结果
→ 比较 2D/3D → 保存或分享 → 回到图鉴继续探索
```

每项功能都应服务这个闭环。不能帮助用户完成“发现、理解、调整、验证、带走”任一步骤的功能，不应抢占一级界面。

### 2.2 三种主要用户模式

#### 探索模式

目标是低门槛获得惊喜。入口包括“随机生成”“上一只/下一只”和“全部猫咪”。界面应强调即时结果，隐藏专业细节。

#### 创作模式

目标是有意图地塑造角色。体型、外观、装备、场景、IP、动作按用户心智分组；撤销、重做和参数锁定让尝试没有成本。

#### 验证模式

目标是判断程序化 3D 是否忠于 Token。2D/3D 对照、固定四视角、Trait 状态和冲突提示属于验证工具，不应与创作控件混为一层。

### 2.3 体验原则

- **直接操控优先**：能通过画布旋转、缩放和角色点击完成的操作，不先要求用户理解表单。
- **每次只做一个重要决定**：参数分组、折叠面板和视角控制用于降低同时暴露的信息量。
- **操作必须可逆**：Trait、体型、装备和身份编辑进入统一撤销/重做历史。
- **状态必须可解释**：Special 覆盖 Background、VR 与眼镜冲突等规则，要在发生时说明原因。
- **等待必须有意义**：加载、切换 Token 和导出要显示阶段、结果或失败原因，避免装饰性的假进度。
- **成果必须可迁移**：分享链接、JSON、PNG、角色卡和 GLB 都是同一角色配置的不同出口。

### 2.4 体验成功标准

- 新用户在 30 秒内能生成并保存第一只猫。
- 用户无需阅读文档即可找到体型、毛色、眼睛、装备和导出。
- 任意一次意外修改最多一次撤销即可恢复。
- 用户能清楚回答“这只猫来自哪个 Token、使用哪些 Trait、为什么某项被覆盖”。
- 从浏览 Token 到完成 2D/3D 对照不超过三个主要动作。

## 3. UI：User Interface，界面视觉哲学

### 3.1 视觉概念：夜间角色实验室

当前界面以深色背景、半透明玻璃面板和明黄色强调色构成“夜间数字工作室”。它既承接 NFT/游戏语境，也能让颜色丰富的角色模型成为最高对比主体。

视觉关键词：

- 深色、克制、沉浸
- 实验室式精确感
- 游戏化但不玩具化
- 轻量科幻，而非复杂赛博朋克
- 猫角色的温度高于工具的技术感

### 3.2 视觉层级

#### 第一层：角色与场景

3D 画布占据完整视口，是所有界面元素的背景与结果区。任何浮层都不能永久遮挡角色头部、脸部或主要装备。

#### 第二层：当前任务

右侧角色配置器、左侧图鉴和 2D/3D 对照属于任务面板。一次只鼓励展开一个主要面板。

#### 第三层：全局控制

语言、天气、固定视角、品牌、Token 身份和底部导出栏属于全局工具，应保持稳定位置和低视觉重量。

### 3.3 色彩语义

| 色彩 | 当前角色 | 使用原则 |
|---|---|---|
| `#11111c` | 舞台底色 | 提供沉浸背景，不表达状态 |
| 半透明深色 Surface | 工具容器 | 与场景分离，但不形成厚重后台感 |
| `#f5d33d` | 品牌黄/强调色 | 当前选择、主操作、Token 身份；同屏不应出现多个同权黄色按钮 |
| 白色/浅灰 | 主文本 | 只用于必要信息和操作标签 |
| 蓝灰色 | 次级说明 | 参数解释、提示和非当前状态 |
| 绿色 | 已完成/有效 | 只表达通过和可用，不作为普通装饰 |
| 红色 | 错误/破坏性状态 | 不用于一般强调 |

### 3.4 组件语言

- 圆角保持 7–16px 的柔和梯度；小控件小圆角，大面板大圆角。
- 玻璃效果用于一级浮层，嵌套内容优先使用边框和明度差，避免层层磨砂。
- 当前选项采用黄色实体填充；悬停只增加亮度，不改变布局。
- Trait 色板用视觉样本表达，文字负责命名，不让颜色成为唯一识别方式。
- 图标必须配合 tooltip 或文本，尤其是天气、灯光和状态操作。
- 动效用于解释状态变化：面板进入、选择切换、相机过渡；不用于持续吸引注意。

### 3.5 排版与信息密度

- 品牌及分区标题使用大写、宽字距，建立实验室仪表感。
- 参数名与操作文本保持正常字距，优先清晰可读。
- 正文和按钮不应低于 12px；当前大量 `.55rem–.69rem` 文本应逐步提升可读性。
- 中文、日文、英文切换时保持信息层级一致，不通过缩小字体强行容纳。
- Token ID 使用等宽数字，强化其档案编号属性。

### 3.6 响应式原则

- 桌面端保持“左证据、中央角色、右控制、底部输出”。
- 移动端改为“中央角色 + 底部抽屉”，而不是把桌面浮层缩小后堆叠。
- 移动端主要操作目标至少 44×44px。
- 打开配置器时，角色仍应保留足够可见面积；必要时自动调整相机 framing。
- 键盘提示只在具备键盘的设备显示，触摸设备显示对应虚拟操作说明。

## 4. UCD：User-Centered Design，以用户为中心的设计哲学

### 4.1 用户不是一种人

#### 收藏者

关心 Token 来源、原图一致性和稀有 Trait。需要图鉴筛选、Token ID、原图证据与分享。

#### 角色创作者

关心“能不能做出我想要的猫”。需要即时参数、锁定、相似变体、身份故事与导出。

#### 3D/游戏用户

关心模型结构、动作、装备挂点、性能和 GLB。需要明确导出边界与技术状态。

#### 普通访客

关心好不好玩、好不好看。需要随机、快速反馈和尽量少的专业术语。

### 4.2 从用户问题组织信息

界面不应按代码模块命名，而应回答用户问题：

| 用户问题 | 对应界面 |
|---|---|
| “这是谁？” | Token ID、原始图片、IP 身份 |
| “它长什么样？” | 体型、外观、固定视角 |
| “它拿着什么？” | 装备与冲突提示 |
| “它在哪里？” | Background、Special、天气 |
| “它会做什么？” | 动作和移动控制 |
| “我能带走什么？” | PNG、角色卡、JSON、GLB、分享链接 |

### 4.3 渐进披露

- 第一级：随机、图鉴、当前角色、保存。
- 第二级：体型、外观、装备、场景、动作。
- 第三级：Trait 状态、实现矩阵、质量模式、身份故事、冲突规则。
- 第四级：开发与审计信息，不进入普通用户主流程。

目前“Trait 状态”和“全部 Trait 实现矩阵”靠近编辑主流程，后续应考虑归入“验证/开发”模式，减少普通用户认知负担。

### 4.4 可访问性

- 所有交互必须支持键盘导航和清晰的 `focus-visible`。
- 状态不能只依赖颜色，应同时提供图形、文字或 aria 描述。
- 画布操作要提供固定视角按钮作为无障碍替代。
- 动效遵守 `prefers-reduced-motion`。
- 面板、抽屉和对照图打开后应管理焦点；关闭后焦点回到触发按钮。
- 图像需要说明其用途：原始 NFT 是视觉证据，3D 画布是可编辑结果。

### 4.5 用户研究与验证方法

每次重要迭代至少验证：

1. **首次使用测试**：用户能否找到随机、编辑和保存。
2. **Token 还原测试**：收藏者能否判断 2D 与 3D 的差异。
3. **参数理解测试**：用户能否预测点击 Trait 后会发生什么。
4. **冲突恢复测试**：Special 或装备覆盖其他参数时，用户是否理解并能恢复。
5. **移动端单手测试**：常用操作是否都在舒适触达区。

## 5. UED：User Experience Design，体验设计执行哲学

UED 负责把 UE 的体验目标、UI 的视觉语言和 UCD 的用户证据转化成一致、可实现、可验收的系统。

### 5.1 页面架构

```text
全局层
├─ 品牌 / 语言 / Token 身份
├─ 固定视角 / 环境快捷项
└─ 输出与分享

探索层
├─ 9901 图鉴
├─ Trait 筛选
└─ 2D 原图证据

创作层
├─ 体型
├─ 外观
├─ 装备
├─ 场景
├─ IP
└─ 动作

验证层
├─ 当前 Trait 状态
├─ 实现矩阵
├─ 2D/3D 对照
└─ 导出与错误反馈
```

### 5.2 交互状态合同

每个可编辑参数至少具备以下状态：

- 默认
- 悬停
- 键盘聚焦
- 已选择
- 已锁定
- 禁用及禁用原因
- 加载中
- 成功
- 错误及恢复动作
- 被其他规则覆盖

例如 Background 被 Special 覆盖时，不能只禁用下拉框；必须显示“由 Special 接管”，并提供清除 Special 的快捷动作。

### 5.3 反馈层级

- **即时反馈**：参数选择、相机变化、面板展开。
- **局部反馈**：Token 加载、图片 fallback、装备冲突、参数覆盖。
- **流程反馈**：PNG/GLB 导出、分享链接生成。
- **系统反馈**：WebGL 异常、资源缺失、性能降级。

反馈应靠近触发位置；只有跨页面或不可逆问题才使用全局提示。

### 5.4 设计令牌原则

现有 CSS 变量应扩展为完整 token，而不是继续在组件中散落颜色与尺寸：

```css
--color-bg-stage
--color-surface-1
--color-surface-2
--color-accent-primary
--color-status-success
--color-status-warning
--color-status-error
--text-primary
--text-secondary
--space-1 ... --space-8
--radius-control
--radius-panel
--motion-fast
--motion-panel
--z-canvas / --z-global / --z-drawer / --z-modal
```

所有组件只能消费语义 token，不应自行定义新的“几乎相同的灰色”或 z-index。

### 5.5 设计与开发交付标准

每个功能在进入开发前应包含：

1. 用户目标与使用场景。
2. 入口、主路径、退出与恢复路径。
3. 空、加载、错误、禁用、冲突状态。
4. 桌面和移动端布局。
5. 键盘、屏幕阅读器和 reduced-motion 行为。
6. 与 CatTraits、history、socket、export 等数据合同的对应关系。
7. 可自动测试的验收标准。

### 5.6 设计质量门禁

- 角色可见面积是否足够？
- 当前主任务是否只有一个视觉焦点？
- 用户是否知道当前 Token 和已应用 Trait？
- 状态变化是否有即时且可理解的反馈？
- 被覆盖或禁用的参数是否解释原因？
- 操作是否可撤销或安全恢复？
- 桌面、移动端、键盘和触摸是否都有完整路径？
- 导出结果是否与当前预览使用同一份配置？

## 6. 当前界面的设计判断

### 应保留

- 中央 3D 舞台和边缘工具的总体格局。
- 深色玻璃与品牌黄构成的鲜明识别。
- 图鉴、Token ID 与 2D/3D 对照组成的证据链。
- 参数分区、撤销/重做、锁定和固定视角。
- 输出动作集中在底部，符合“完成创作后带走成果”的顺序。

### 应优化

- 减少右侧面板首屏同时出现的搜索、Token、审计、矩阵和参数内容。
- 将“创作模式”和“验证模式”分开，普通用户默认不看开发状态。
- 提高小字号和低对比说明文本的可读性。
- 统一重复的 tab grid、圆角、阴影、z-index 和状态颜色。
- 明确主按钮：随机生成、保存 PNG、导出 GLB 不应长期同权。
- 移动端采用底部抽屉和自动相机避让，避免浮层遮挡角色。
- 为 Special 覆盖、资源 fallback 和导出失败提供靠近操作点的恢复入口。

## 7. 最终设计准则

1. **角色优先于工具。**
2. **结果优先于参数。**
3. **证据优先于宣称。**
4. **可逆优先于谨慎确认。**
5. **渐进披露优先于一次展示全部能力。**
6. **语义一致优先于局部视觉新奇。**
7. **真实状态优先于装饰性反馈。**
8. **同一份 CatTraits 必须贯穿预览、分享与导出。**

Liberty Cat Studio 的设计目标不是让用户感受到系统有多复杂，而是让复杂的程序化 3D 系统表现得像在和一只角色直接相处、塑造并确认它。
