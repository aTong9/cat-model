# Liberty Cats 参数化 3D 与小游戏开发路线

## 1. 目标定义

将 Liberty Cats 的二维特征体系重建为可配置的 Three.js 角色系统，使同一份参数能够：

1. 在网页中实时生成和预览猫咪；
2. 稳定复现集合中每个 token 的外观；
3. 导出干净、可复用的 GLB 角色资产；
4. 直接进入跑酷、收集、竞速、派对等小游戏；
5. 在新增特征、动作和玩法时不必重复维护模型代码。

“支持所有猫”应定义为：集合中每个 token 都有一份已保存的规范化参数记录，并能通过自动测试生成对应 3D 角色。它不等于手工制作约一万个独立 GLB。

## 2. 当前项目的基础与主要缺口

### 可复用部分

- Vue、Pinia、Three.js 和 Vite 已经搭好。
- 已有毛色、眼睛、表情、装备、背景、Special 等参数。
- `CatModel`、`EquipmentFactory` 和特殊场景已经形成初步的程序化建模结构。
- 已有随机种子、角色预设、当前画布 PNG 保存和 GLB 导出入口。
- `CatCanvas.vue` 已经有 WASD、跑步、跳跃和简单物理交互，可作为玩法原型。

### 关键缺口

1. **数据覆盖没有被证明**：当前配置只有少量已知属性和 15 个左右的预设样本，没有集合级 token 清单，也没有逐 token 验证报告。
2. **生成逻辑耦合在 UI 中**：角色装配、场景、输入、天气、散落装备和导出都围绕 `CatCanvas.vue` 工作，不利于批处理、测试和多款游戏复用。
3. **GLB 导出边界不正确**：当前导出 `scene`，会把地面、灯光、场景物件等一起打包。游戏资产应默认只导出角色根节点及其动画。
4. **动画不是标准角色动画资产**：现有动作主要是运行时程序动画。若要让 GLB 在其他引擎或独立游戏中复用，需要骨骼、蒙皮和 `AnimationClip`，或者明确采用“刚体节点动画”的轻量方案。
5. **小游戏资产约定尚未建立**：缺少统一尺寸、朝向、脚底原点、碰撞体、挂点、LOD、材质预算和性能预算。

## 3. 先解决数据与版权，再扩展建模

### 数据来源

不要依赖 OpenSea 活动页逐张抓图。应优先获得或整理以下资料：

- 集合合约地址、链、token ID 范围；
- 每个 token 的原始 metadata URI 和规范化属性；
- 原始分层美术素材或官方 trait 列表；
- Special/Legendary 等非普通组合的明确规则；
- 缺失、销毁、重复、未揭示 token 的处理规则。

建议生成三个版本化文件：

```text
data/
  collection.manifest.json       # 合约、供应量、schema 版本、来源
  tokens.normalized.json         # tokenId -> 标准参数
  trait-catalog.json             # trait -> 3D 实现、别名、稀有度、状态
```

OpenSea、第三方统计和当前 README 对集合数量可能给出不同数字。最终数量必须以链上合约与原始 metadata 的审计结果为准。

### 权利边界

把 NFT 图片重建成 3D、批量导出并放入游戏，可能涉及原项目美术、商标和商业使用授权。开发前应确认团队拥有对应授权，特别是：

- 是否允许衍生 3D 模型；
- 是否允许商业游戏和再分发 GLB；
- 持有人权益是否只覆盖其持有 token；
- 官方名称、Logo 和营销素材是否可用。

技术上能生成不代表法律上可以公开分发。

## 4. 推荐架构

### 单一规范化参数

定义稳定的 `CatTraits`，不要让 UI 文本直接成为内部 ID：

```js
{
  schemaVersion: 1,
  tokenId: 9038,
  body: 'base-v1',
  fur: 'tuxedo',
  eyes: 'relaxed',
  face: 'smile',
  headGear: null,
  handGear: 'hiking-backpack',
  background: null,
  special: 'time-traveler',
  palette: {},
  seed: 9038
}
```

保留显示名称和 metadata 原值，但通过 alias 表映射到稳定 ID，例如 `VR`、`Vr` 都映射到 `vr`。

### 抽出纯角色工厂

建议把角色生成从 Vue 生命周期中抽离：

```text
src/core/
  normalizeTraits.js
  validateTraits.js
  createCatAssembly.js
  assetRegistry.js
  exportCharacterGlb.js
  disposeAssembly.js
```

理想接口：

```js
const assembly = await createCatAssembly(traits, {
  quality: 'game',
  animationSet: 'standard',
})

scene.add(assembly.root)
```

`assembly` 至少提供：

- `root`：只包含角色的根节点；
- `clips`：idle、walk、run、jump、hit、celebrate；
- `sockets`：head、face、back、leftHand、rightHand；
- `collider`：胶囊体或简化碰撞信息；
- `metadata`：token 与 trait 信息；
- `dispose()`：释放几何体、材质和纹理。

预览器、导出器和所有小游戏都调用同一个工厂。

### 特征实现分层

把特征分成四类，避免所有变化都写进一个巨大模型类：

1. **材质特征**：毛色、纹理、花纹、眼色；
2. **形态特征**：眼型、嘴型、耳朵、体型；
3. **插槽附件**：帽子、眼镜、背包、手持物；
4. **整套替换/Special**：独立身体、服装或完整主题角色。

普通组合应共享几何体和纹理。Legendary/Special 可以使用独立 GLB，但仍需遵守相同根节点、动画和碰撞约定。

## 5. GLB 导出标准

不要默认导出整个 Three.js 场景。建议只导出 `assembly.root`，并制定以下约定：

- 单位：1 Three.js unit = 1 米；
- 轴向：Y 向上，角色面向 +Z 或 -Z，项目内固定一种；
- 原点：脚底中心；
- 角色高度和碰撞体尺寸统一；
- 节点名、材质名和 socket 名稳定；
- 纹理使用可移植格式，避免依赖浏览器 Canvas 或外部 URL；
- 导出前更新 world matrix，并剔除灯光、相机、辅助线和环境对象；
- 将 token 属性写入根节点 `extras`；
- 导出后重新加载 GLB 做回归测试。

建议输出两类 GLB：

- `character.glb`：带骨骼、动画、附件，供游戏使用；
- `display.glb`：可选地包含展台或展示姿势，供展示页面使用。

若所有 token 都提前导出，文件量和重复数据会很大。更推荐在网页游戏中按参数运行时装配，仅对下载、缓存或外部引擎需求按需导出 GLB。

## 6. 动画与游戏运行时建议

### 动画选择

长期建议使用统一骨架和蒙皮模型。最低动画集：

- idle
- walk
- run
- jump_start / jump_loop / land
- hit
- interact
- celebrate

附件通过 socket 跟随骨骼。表情可以用 morph target，或继续使用可替换的眼睛/嘴巴节点。

如果暂时不做骨骼，可先用节点层级和程序动画完成第一款小游戏，但要把动画控制封装成统一 `CharacterController`，避免玩法直接操作模型内部节点。

### 推荐的第一批小游戏

按开发成本排序：

1. **收藏品跑酷**：复用当前移动和跳跃，收集金币/鱼干，验证碰撞、相机、动画和 GLB。
2. **装备争夺派对**：场地中拾取装备，装备改变技能或分数，复用现有散落装备和射线交互。
3. **障碍竞速**：加入检查点、计时、移动平台和排行榜。
4. **Special 主题关卡**：时间旅行传送门、富士山攀登、雷暴躲避等，每个 Special 变成一个玩法主题。

第一款游戏不建议先做联网、链上登录或多人同步。先证明同一角色工厂可以同时服务预览、导出和单机玩法。

## 7. 性能预算

在开发游戏前设置可衡量预算，例如桌面端单角色：

- 三角面：普通角色 20k–50k 以内；
- 材质：尽量 1–4 个；
- 纹理：优先 1K，必要时 2K；
- Draw calls：尽量低于 10；
- 同屏多角色时使用共享几何体、共享材质、纹理图集和实例化；
- SDF/程序几何的高质量版本用于导出，游戏版本使用缓存或简化网格；
- 加入 `static`、`game`、`thumbnail` 三档质量。

具体阈值需要在目标设备上实测，上述数字只是初始预算，不是最终结论。

## 8. 自动化验证

“所有猫都支持”需要机器验证，而不是人工承诺。建议建立：

- schema 校验：每个 token 的属性都能规范化；
- catalog 校验：每个 trait 都有实现或明确标记为待实现；
- 组合测试：附件不穿模、Special 不与普通规则冲突；
- 缩略图回归：固定相机批量渲染并做像素差异检查；
- GLB 回读：导出后用 `GLTFLoader` 加载，检查节点、动画、材质、包围盒；
- 性能报告：三角面、材质、纹理、文件大小、生成耗时；
- 覆盖率报告：总 token、成功、警告、失败、未实现 trait。

不要一开始渲染全部 token。先选择约 50 个“覆盖集合”，确保每个 trait 和主要冲突组合至少出现一次，然后扩到全量。

## 9. 分阶段实施路线

### 阶段 0：权限与数据审计

- 确认衍生开发与 GLB 分发授权；
- 确认合约和 metadata 来源；
- 导出全量 token/trait 清单；
- 建立未知值、别名和 Special 清单。

完成标准：能回答“究竟有多少 token、多少唯一 trait、哪些是例外”。

### 阶段 1：统一 schema 和角色工厂

- 将 trait 配置整理为单一、可验证的数据源；
- 建立稳定 ID 和 alias；
- 把 `CatModel`、装备装配从 Vue 中抽成 `createCatAssembly()`；
- 让现有预览器改用新工厂。

完成标准：相同参数在预览、截图和测试中得到同一角色。

### 阶段 2：游戏级角色规范

- 确定骨架、尺寸、朝向、原点和 sockets；
- 完成标准动作集和碰撞体；
- 给模型增加质量档与性能统计；
- 修复附件穿模和 Special 规则。

完成标准：角色可稳定进入一个空白测试关卡移动、跳跃和切换装备。

### 阶段 3：可靠 GLB 管线

- 只导出角色根节点；
- 导出动画、extras 和纹理；
- GLB 自动回读验证；
- 支持当前角色、指定 token 和批量覆盖集导出。

完成标准：导出的 GLB 在当前项目的新场景中重新加载后外观与动作一致。

### 阶段 4：第一款小游戏

- 建立 `GameShell`、输入、相机、碰撞、关卡和角色控制器；
- 先做收藏品跑酷；
- 角色选择器直接读取同一 `CatTraits`；
- 加入暂停、重开、计分和移动端控制。

完成标准：至少 50 个覆盖 token 都能无特殊代码进入游戏。

### 阶段 5：全量覆盖与内容扩展

- 补齐全部 trait 和异常 token；
- 执行全量生成审计；
- 建立缓存和按需加载；
- 再扩展竞速、派对或 Special 主题关卡。

## 10. 近期最值得先做的任务

建议下一轮开发只聚焦以下事项：

1. 获取可靠的全量 metadata，并生成 trait 覆盖报告；
2. 将 `src/config/traits.js` 整理为单一、可验证的数据源；
3. 抽出不依赖 Vue/DOM 的 `createCatAssembly(traits)`；
4. 修改 GLB 导出，使其只导出角色并能自动回读；
5. 选 50 个覆盖 token 做视觉基准；
6. 用新角色工厂做一个最小跑酷测试场景。

在以上六项完成之前，不建议继续堆叠更多 UI、天气特效或独立 Special 场景，因为那些工作无法证明全量覆盖，也会提高后续重构成本。

## 11. 当前不确定事项

- 不确定 OpenSea 展示的所有数据是否能通过公开接口稳定、完整地获取。
- 不确定项目团队是否拥有原始分层素材和衍生 3D/游戏授权。
- 不确定集合最终应覆盖的准确 token 数量；公开页面存在不同口径，应以链上和 metadata 审计为准。
- 不确定现有程序化 3D 外观需要达到“特征可识别”还是“逐像素/逐造型高度还原”；两者成本差别很大。
- 不确定目标小游戏优先支持桌面、移动端还是微信/小程序 WebView，这会影响性能预算和输入系统。
- 不确定 GLB 的主要消费者只是当前 Three.js 项目，还是还包括 Blender、Unity、Godot 等工具；这会影响骨架、材质和扩展兼容策略。
